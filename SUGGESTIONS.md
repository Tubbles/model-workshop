## Workshop

- One shared FreeCAD scaffolding module. `model/kbdkid4/scripts/board_step.py` and `model/kbdkid5/scripts/freecad_common.py` both carry the freecadcmd scaffolding and the STL export (their module docstrings), the second a port of the first, and `model/solder-spool-axle/` and `model/camera-arm/` reach into kbdkid4's directory for it through their `sys.path` line. A module beside `docker/` would let every project import one copy. Not done in the move (2026-10-21), whose promise was byte-identical STLs with only path changes, and the two copies' STL export settings would have to be compared first.
- The kbdkid4 artifacts name only this repository's commit. Which kbdkid4 CI run and commit gave the STEP and the board files is printed in the job log by `.github/actions/kbdkid4-board`, but not in the download, so two downloads with the same name can hold different parts after a board change in kbdkid4. Writing the kbdkid4 commit into the artifact name or into a small text file inside it would make a download say which board it was built from. Not done because the user asked only for the STEP to come from kbdkid4's CI.
- A keyboard's merge job (work items 024 and 025, `.github/workflows/ci.yml`) uploads the merged artifact, then deletes the intermediates. A server error partway through the deletes leaves some deleted, and rerunning the failed merge then uploads a second, partial `<project>-<short commit hash>` or `<project>-test-<short commit hash>` beside the full one. Only "re-run all jobs" recovers (024's review, upload-artifact issues 678 and 751), which CLAUDE.md (Main's CI ends green) now prescribes, but even that leaves a second full zip and some intermediates on the run page.
- A rerun of failed kbdkid4 jobs looks up kbdkid4's latest successful run again (`.github/actions/kbdkid4-board`), so after a kbdkid4 push in between, the merged `kbdkid4-<short commit hash>` mixes STLs of two boards. This held before work item 024 too, but the merge now hides it inside one artifact (024's review).
- The `kbdkid4-pcb` job (`.github/workflows/ci.yml`) uploads `kbdkid4-test-<short commit hash>` itself since work item 025, so by CLAUDE.md's Starting a project it would be named `kbdkid4-test`. Not renamed in 025, since a job's name is its check's name.
- A CI step that checks the workflow's artifact layout, as 025's local check did (`tmp/025/check_ci.py`, untracked): each export job uploads once, at its end, its STLs all parts or all tests, and each merge pattern matches its own group's intermediates only. A job that mixes the two or a pattern that matches too much would then fail on the push rather than show up in a download. Not done since 025 asked for the split only.

A check over the exported mesh's triangles would cover them. Not done in 029, whose arm prints on supports.
- The camera bar's loft (`bent_bar()`) still meets the bend forward and the bar under the case at zero radius, kinking 17.4 and 14.2 degrees (work item 033's review), the path's only corners without an arc. Arcs there need room the 4 mm loft lacks: an S curve for its 1.2 mm step in x at 8.5 mm radius takes about 6.3 mm, so the riser's x or the loft's length would have to give, and the twist would move into a two profile sweep.

## Placement solver

- **The least broken pose from a stationary start.** `least_broken_alone()` (`tools/placement/solver.py`) runs SLSQP from one start, and a start where the least margin's slopes cancel stays there: a body in a 2 by 2 block with its target at the block's middle is reported at (0, 0) breaking by 2.5, where (0.5, 0) breaks by 2.0 (round 8's review, `tmp/review_round8/probe_least_broken.py`, untracked). A few spread starts would find the better pose. Left out of the first version (2026-10-22): the pose only explains a failure, and it is wrong only in how much it breaks.
- **COBYQA after an SLSQP end that is already optimal.** When SLSQP ends feasible but reports "Positive directional derivative for linesearch", the COBYQA fallback still runs: 20 s for a MOST_CLEARANCE part with a body of radius 0 against a wall (round 9's implementer). Accepting a feasible SLSQP end the fallback cannot improve would save that. Not done, since work item 016 took no new features after its first review.
- **The tried line's wording** in `option_outcome()` (`solver.py`): "breaks a rule by" counts the reach as a rule, and "no free pose in its window" is also said when the only free poses lie beyond the reach, while `explain()` lists no row for the reach. Left in the first version, since the rows under it name the other rules.
- **The reach cut loses a sliver.** `place_by_map()` cuts the map with `space.within_reach()`, a polygon inscribed in the reach circle, so free poses lying only between its chords and the circle (a band up to 7.5e-5 times the reach wide, 0.23 µm at a reach of 3) are missed, and the SLSQP runs from the start and the target alone can miss them too: a made up case reports "not placed" where round 8's code placed it (round 9's review, `tmp/review_round9/probe_reach_sliver.py`, untracked). Cutting with the circle grown by the arcs' error, the runs holding the exact reach, would close it. Left out of the first version (2026-10-22): no printed part tells such a band apart.
- **Smaller gaps from round 9's review.** An unplaced part that took an alternative is drawn with its own target and window, not the alternative's. `MapSummary` describes the map before the reach cut, so its most clearance point can lie beyond the reach. The reach constraint's multiplier is not reported, and another row carries the binding mark. With several pocket starts, COBYQA is skipped once any SLSQP start succeeds, so a pocket whose SLSQP run failed is not retried.
- **Tests the core suite lacks**, from round 8's review (mutants in `tmp/review_round8/mutate_core.py`): a solo part beyond its reach getting a best pose, how a rule's multiplier is taken from its rows (summed or the last), `WINDOW_SLACK` at 0 or the window ignoring a rule's minimum (`evaluate.py`), one conditional over several instances, an apart in height rule binding by its plan margin, `explain()` within the window, group runs from one start set, reach rows counted toward clearance, and MOST_CLEARANCE with no rule at all.
- **Maps per angle.** `space.py` builds a part's configuration space map at its start angle, so an angle degree of freedom is found by SLSQP alone. The research (`work/research/placement-solver.md`, section 4, untracked) has a map per angle slice. Not built because no model turns a part yet.
- **Solids that are not prisms**, such as the camera arm's tilted camera case, would go through trimesh meshes and python-fcl or coal distances as constraints, by the research (section 4, 3D). Added when a model needs one.
